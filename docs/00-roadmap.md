# go-rpg 3ヶ月ロードマップ

## ゴール

**3ヶ月後（12週後）に「RPGとして遊べる基盤」が完成している状態。**

具体的には、次の一連の流れが 1本のビルドで通ること。

```
タイトル画面 → フィールドマップを歩く → NPCに話しかける → 敵とエンカウント
→ コマンドバトル → 勝利して経験値取得 → メニューで装備/アイテム → セーブ → ロードで再開
```

素材のクオリティやシナリオ量は目標に含めない。**「作り続けられる設計」** が本当の成果物。

## 前提と進め方

| 項目 | 内容 |
| --- | --- |
| 言語 / ライブラリ | Go 1.25+ / [Ebitengine](https://ebitengine.org/) v2 |
| 1日の作業時間 | 30〜60分 |
| 週の稼働 | 週5日（残り2日は予備日・復習日） |
| 全体 | 12週 × 5日 = **全60日** |
| 1日の粒度 | 「30分で終わり、終わったら必ず画面で動く」単位まで分割 |

### 大原則: 毎日、画面が動く

各 Day には必ず **動作確認手順** が書いてある。`make run` してその通りに動けばその日は完了。
テストだけ書いて終わる日、画面が変わらない日は作らない（リファクタ回のみ例外で、その場合は
「壊れていないこと」を画面で確認する）。

## 設計パターンの導入計画

「最初から完璧な設計」は狙わない。**動くものを作る → 痛みが出る → パターンで解決する** の順で進める。
これが実務でのリファクタリングの流れそのもので、パターンを「なぜ必要か」ごと身につけられる。

| 週 | 出てくる痛み | 導入するパターン |
| --- | --- | --- |
| W1 | 更新と描画が混ざる | **Game Loop**（Ebitengine が提供） |
| W1 | `if ebiten.IsKeyPressed(...)` がロジックに散らばる | **Input Abstraction / Adapter** |
| W2 | 「アニメの定義」と「再生中の状態」が混ざる | 定義とインスタンスの分離 |
| W3 | キャラの状態分岐が `if` の山になる | **State** / **Strategy**（NPC の行動） |
| W4 | 同じタイル画像を大量に持ってメモリを食う | **Flyweight**（タイル定義の共有） |
| W5 | 当たり判定と描画とカメラが `Game` に同居する | 責務分離（`physics` / `camera` の独立） |
| W6 | `Game` が全部の状態を抱えて肥大化する | **State（Scene）＋ Scene Stack** |
| W7 | 会話・選択肢の分岐がベタ書きになる | **Command**（会話を命令列として扱う） |
| W8 | バトルの進行が巨大な switch になる | **有限状態機械（FSM）** |
| W9 | 「攻撃」「魔法」「逃げる」の追加のたび既存コードを触る | **Command + Strategy**（行動と敵AI） |
| W10 | 敵やアイテムの追加でコードを再ビルドする羽目になる | **データ駆動 + Repository + Factory** |
| W11 | 「HPが0になった」を色々な場所が知りたがる | **Observer / Event Bus** |
| W12 | 構造体が肥大化し、機能追加のたび全体を触る | **Component 指向（ECS への布石）** |
