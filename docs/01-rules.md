# 開発ルール

3ヶ月続けるための運用ルール。**守れないルールは作らない**ので、意図的に少なくしてある。

---

## 1. 1日のサイクル（30〜60分）

毎日この順番で進める。所要時間の目安つき。

| # | やること | 目安 |
| --- | --- | --- |
| 1 | `docs/plan/week-NN.md` の当日分を読む | 2分 |
| 2 | `make log` で今日のログを作る | 1分 |
| 3 | 実装する | 20〜40分 |
| 4 | `make run` で **画面で動作確認** | 3分 |
| 5 | `make check`（fmt + vet + test）を通す | 2分 |
| 6 | ログに「やったこと・詰まったこと・次回」を書く | 5分 |
| 7 | コミット & プッシュ | 2分 |

### 時間切れになったら

**途中でも必ずコミットして終わる。** コミットメッセージに `wip:` を付ける。
「キリのいいところまで」は禁止。翌日の自分は今日の自分より記憶が薄い。
中断するときは、ログの「次回やること」に **次に触るファイル名と関数名** まで書く。

---

## 2. 記録のルール

### 作業ログ

- 置き場所: `docs/logs/YYYY-MM-DD.md`
- 作成: `make log`（`docs/logs/TEMPLATE.md` から生成される）
- **1日1ファイル。必ず書く。** 「何もできなかった」も1行で残す（それも記録）。

書く内容は 4 つだけ。

1. **やったこと** — 実装した内容を箇条書きで
2. **動作確認** — 画面で何が起きたか（スクショがあれば `docs/logs/img/` に置く）
3. **詰まったこと / 学んだこと** — エラーメッセージと解決方法をそのまま貼る
4. **次回やること** — 次に触るファイル・関数まで具体的に

### 進捗表

`docs/PROGRESS.md` の該当 Day のチェックボックスを埋める。
週の終わりに眺めて、遅れていたら **予備日で取り戻すか、計画そのものを削る**。
計画を守るために品質を落とすのは本末転倒なので、削る方を優先する。

## 3. Git のルール

### ブランチ

| ブランチ | 用途 |
| --- | --- |
| `main` | 常に `make run` が通る状態を保つ |
| `feat/dayNN-<内容>` | 1日の作業用。例: `feat/day07-player-move` |

1日1ブランチ。終わったら `main` へマージ（自分ひとりなので早送りマージでよい）。

### コミットメッセージ

[Conventional Commits](https://www.conventionalcommits.org/) に従う。

```
<type>(<scope>): <日本語で要約>

<なぜそうしたかの補足（任意）>
```

| type | 使うとき |
| --- | --- |
| `feat` | 機能追加 |
| `fix` | バグ修正 |
| `refactor` | 挙動を変えない内部改善 |
| `test` | テストの追加・修正 |
| `docs` | ドキュメント |
| `chore` | ビルド・設定・依存の更新 |
| `wip` | 時間切れの途中保存（後で潰す前提） |

例:

```
feat(player): 十字キーでプレイヤーを4方向に移動できるようにする

移動速度は 1 フレームあたり 1.5px。TileSize(16px) の約 10 分の 1 にして
タイル境界での引っかかりを避ける。
```

### コミットの粒度

**「1コミット = 1つの意味のある変更」。** 30分の作業なら 1〜3 コミットが目安。
`make check` が通らない状態を `main` に入れない（`wip:` はブランチ上でのみ許可）。

---

## 4. コードの完了条件（Definition of Done）

その日の作業を「完了」と呼べるのは、次を **すべて** 満たしたとき。

- [ ] `make run` で起動し、その日の動作確認手順どおりに動く
- [ ] `make check`（gofmt / go vet / go test）が通る
- [ ] 追加した公開関数・型に doc コメントがある
- [ ] `docs/logs/YYYY-MM-DD.md` を書いた
- [ ] `docs/PROGRESS.md` のチェックを埋めた
- [ ] コミット & プッシュした

---

## 5. テストの方針

ゲームは「描画」と「入力」がテストしづらい。なので **テストする対象を最初から決めておく**。

| 対象 | テストする？ | 理由 |
| --- | --- | --- |
| ダメージ計算・レベルアップ・所持金 | **必ず書く** | 純粋関数にできる。バグると気づきにくい |
| 当たり判定・座標変換・タイル座標計算 | **必ず書く** | 数値バグは目視で見つけにくい |
| ステートマシンの遷移 | **必ず書く** | 分岐が多く壊れやすい |
| セーブデータの入出力 | **必ず書く** | 壊れるとプレイヤーの時間を奪う |
| 描画（`Draw`） | 書かない | 目で見た方が速い |
| 入力デバイスの読み取り | 書かない | 抽象化した先（`input.Provider`）をフェイクで差し替えて代替 |

**「テストしやすい形に切り出す」こと自体が設計の練習**になる。
テストが書きづらいと感じたら、それは設計が間違っているサイン。

---

## 6. リファクタリングのルール

- **1週間に1回、リファクタ専用の日を設ける**（各週の Day 5 がそれ）
- リファクタの日は **機能を足さない**。挙動が変わっていないことを `make run` と `make test` で確認する
- 「パターンを使いたいから使う」は禁止。**痛みが出てから入れる**
- リファクタのコミットは `refactor:` 単独にする（機能追加と混ぜない）

---

## 7. 詰まったときの逃げ道

30分で解決しなかったら **その日は撤退する**。ログに以下を書いて終わる。

- 何をしようとしたか
- どんなエラーが出たか（メッセージをそのまま貼る）
- 試したこと

翌日、頭が冷えた状態で読み返すと解けることが多い。それでもダメなら **その機能を1つ簡単にする**
（例: 斜め移動をやめて4方向だけにする）。3ヶ月続けることが最優先。
